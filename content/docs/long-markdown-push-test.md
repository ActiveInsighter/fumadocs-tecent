# 长 Markdown 推送测试

> 这是一篇专门用于验证长 Markdown 文件写入、Git 提交、分支隔离以及 Fumadocs 内容目录兼容性的测试文档。本文只存在于测试分支，不应影响 `main`。

## 1. 测试目标

本测试主要验证以下事项：

1. 能否从 `main` 创建一个完全独立的测试分支。
2. 能否向 `content/docs/` 写入一篇较长的 Markdown 文档。
3. 能否正确保存中文、英文、代码块、表格、引用、列表、链接风格文本以及数学公式。
4. 能否在写入后重新读取文件，确认远端分支已经真实存在该文件。
5. 能否保证整个测试过程中不修改 `main`。

为了让测试更接近真实知识库文档，下面会混合使用多层标题、长段落、列表、表格、代码块和数学表达式。

## 2. Markdown 基础结构

Markdown 的一个重要优势是纯文本格式足够简单，同时又可以承载相对复杂的结构。对于 Fumadocs 这类文档系统而言，源文件通常只是普通的 Markdown 或 MDX，然后在构建阶段被解析为页面。

一篇较长的知识库文档往往包含章节、子章节、公式、示例、注意事项、代码片段和大量说明文字。只要文件编码、Frontmatter 和 Markdown 语法正确，文档长度本身通常不会成为 GitHub 内容写入的主要限制。

### 2.1 段落测试

这一段用于验证较长中文内容能否完整保存。实际生产环境中，文档往往来自 AI 回复、课程笔记、题库解析、技术文档或自动化工作流。文档在进入 Git 仓库之前可能已经经历清洗、标题生成、slug 生成、标签生成、Markdown 规范化等步骤，因此最终写入仓库时最重要的是保证字符集、换行符、文件路径和提交目标分支正确。

如果这些基础条件都满足，那么后续由 Fumadocs 构建器负责把源文档转换成最终页面。也就是说，GitHub 写入测试和站点构建测试虽然相关，但实际上属于两个阶段：前者验证“文件能否进入仓库”，后者验证“文件进入仓库之后能否被站点正确识别和构建”。

## 10. 长文本压力段落 A

在一个真实的文档自动发布系统中，内容从生成到最终上线通常会经历多个阶段。第一阶段是内容生成，例如 AI 回复、人工编辑结果或者从外部资料整理出的 Markdown。第二阶段是内容规范化，包括统一标题、删除多余标记、修复公式、整理代码块、生成 Frontmatter、生成 slug 和摘要。第三阶段是持久化，可以先写入数据库，也可以直接进入 Git 仓库，具体取决于系统是否需要保存中间状态。第四阶段是发布，把 Markdown 写入 Fumadocs 对应的内容目录，并触发站点构建。第五阶段是构建产物处理，例如生成静态 HTML、搜索索引、PDF 或打包文件。第六阶段是部署和缓存更新，使最终用户能够访问新页面。

这个过程中最容易出现的问题并不是 Markdown 本身，而是状态同步。例如数据库已经显示“发布成功”，但 GitHub 实际写入失败；或者 GitHub 已经成功提交，而构建系统因为依赖安装失败、MDX 语法错误、超时或平台网络故障而没有部署；又或者构建已经成功，但 CDN 缓存仍然指向旧版本。因此一个可靠的工作流应当把“内容生成成功”“Git 提交成功”“构建成功”“部署成功”视为不同状态，而不是简单使用一个布尔值表示整个链路成功。

## 11. 长文本压力段落 B

如果未来需要批量推送压缩包中的文档，一个比较合理的处理流程是先在本地工作区解压，然后遍历 Markdown 文件，检查路径是否合法，规范化文件名，并读取每个文件的 Frontmatter。对于同名文件，需要提前决定是覆盖、跳过还是自动重命名。对于目录结构，需要决定是否完全保留压缩包中的原始层级，还是重新映射到 Fumadocs 的章节目录。对于 meta.json，则需要谨慎处理，因为它不仅仅是普通内容文件，还可能决定侧边栏页面顺序和章节可见性。

批量导入时还要关注一次提交和多次提交的选择。如果整个压缩包属于同一个逻辑任务，通常一次提交包含全部文件会更容易回滚，也更容易审查。但如果文件数量非常多、单个文件很大，或者需要逐文件记录发布状态，那么分批提交可能更合理。测试分支在这里很重要，因为它允许先验证构建结果，再决定是否合并到生产分支。

## 12. 长文本压力段落 C

Git 本身非常适合管理文本文件，因为每一次变更都可以追踪。对于知识库而言，这意味着不仅能知道当前页面是什么内容，还能知道某一段内容是什么时候加入的、由哪个提交引入、之后经过哪些修改。与直接把文档存到对象存储相比，Git 仓库更适合管理“源内容”；对象存储则更适合保存 PDF、图片、压缩包等构建产物。两者并不冲突，可以分别承担源文件版本管理和二进制产物托管的职责。

对于自动化系统而言，分支也是非常有用的隔离机制。生产内容可以固定进入 `main`，实验性内容、批量导入预览、AI 自动修改则先进入独立分支。只要构建平台支持分支预览，就可以在合并前看到最终页面效果。如果发现路径错误、Frontmatter 缺失、公式解析失败、图片链接失效或者导航层级不合理，直接删除测试分支即可，不会污染生产历史。

## 13. 长文本压力段落 D

长 Markdown 文件对系统的挑战主要来自传输、解析和渲染三个方面。传输阶段需要确保请求体大小没有超过 API 限制；解析阶段需要避免因为错误的 MDX 语法导致编译器失败；渲染阶段则需要关注页面体积和浏览器性能。纯 Markdown 文本通常压缩率很高，因此几十 KB 或几百 KB 的文档在网络层面并不算大，但如果文档中嵌入大量 Base64 图片、超大 JSON、复杂 Mermaid 图或大量高亮代码，就会显著增加构建时间和页面体积。

更理想的做法是把图片放在对象存储或仓库静态资源目录中，而不是直接嵌入 Markdown。这样 Markdown 文件仍然保持纯文本特性，Git diff 也更加清晰。对于 PDF 等衍生产物，也不建议直接塞进普通内容目录，而应放到专门的下载存储中，然后在文档页面中提供下载入口。

## 14. 长文本压力段落 E

当自动化流程需要处理很多文档时，幂等性非常重要。假设一个任务因为网络问题重试三次，如果系统每次都创建一个新文件，就可能得到三个几乎完全相同的页面。更好的方案是给每个任务或消息分配稳定的发布键，例如使用数据库记录 ID、任务 ID 或规范化 slug 组合。这样重复执行时能够识别目标文件已经存在，并选择更新现有文件而不是重复创建。

同样，数据库中的发布状态也应该尽量记录具体信息，例如仓库、分支、提交 SHA、文件路径、构建 run ID、部署 URL、失败阶段和错误摘要。这样出现问题时，系统可以准确知道失败发生在哪里，而不是只看到一个模糊的“发布失败”。

## 15. 长文本压力段落 F

在生成 Markdown 时，Frontmatter 是一个容易被忽略的部分。标题和 description 一般不复杂，但一旦加入数组、嵌套对象、日期、标签或包含特殊字符的字符串，就要注意 YAML 转义。自动生成 Frontmatter 时最好使用可靠的 YAML 序列化器，而不是简单拼接字符串。正文则要重点处理三类语法冲突：代码块中的反引号、数学公式中的特殊符号，以及 MDX 模式下可能被解释成 JSX 的尖括号。

如果源内容只是标准 Markdown，优先使用 `.md` 可以减少 MDX 特有语法带来的风险。如果确实需要 React 组件、Tabs、Cards 或自定义组件，再使用 `.mdx`。这也是本测试文件选择 `.md` 的原因：它更适合作为纯文档写入链路的基础压力测试。

## 16. 长文本压力段落 G

导航配置通常决定一个已经存在于内容目录中的文件是否会显示在侧边栏中。如果 meta.json 使用显式 pages 数组，那么新文件虽然已经被构建系统发现，却可能不会自动出现在导航里。因此真实发布工作流除了创建 Markdown，还可能需要同步更新所属目录的 meta.json。这个更新必须避免竞态：如果两个任务同时读取旧的 meta.json，然后分别追加自己的页面并写回，后写入的任务可能覆盖前一个任务的修改。

解决这种并发问题可以使用队列串行化、乐观锁、基于最新 SHA 的更新重试，或者把导航设计成自动扫描文件而不是每次修改 meta.json。具体选择取决于文档站是否需要严格控制页面顺序。

## 17. 长文本压力段落 H

测试分支还有一个重要用途，就是验证部署平台对分支构建的支持。理想情况下，每次向测试分支推送后，CI 会运行 lint、typecheck、build 等步骤。如果平台支持 Preview Deployment，还会产生一个临时访问地址。这样自动化系统就能进一步检查页面是否返回 200、是否包含预期标题、搜索索引是否生成，以及链接是否可访问。

如果仓库没有对普通分支配置自动构建，那么 GitHub 写入成功仍然说明“文档推送能力”已经验证通过，只是“部署能力”需要单独测试。二者最好不要混在同一个状态中。

## 18. 长文本压力段落 I

对于包含大量数学内容的知识库，还需要特别验证公式格式。Markdown 渲染器与数学插件的组合不同，有的项目偏好单美元符号作为行内公式、双美元符号作为块级公式，有的项目通过 remark-math 和 rehype-katex 处理。自动清洗文档时，应避免把代码中的美元符号误当作公式，也要避免破坏 LaTeX 命令中的反斜杠。

示例：若二次函数为 $f(x)=ax^2+bx+c$，其判别式为 $\Delta=b^2-4ac$。当 $\Delta>0$ 时有两个不同实根，当 $\Delta=0$ 时有两个相同实根，当 $\Delta<0$ 时在实数范围内无根。这个简单示例同时包含中文、行内公式、反斜杠和比较符号，可用于检查文本传输是否完整。

## 19. 长文本压力段落 J

长文档通常还会包含大量代码。代码块的关键要求是不要让清洗程序随意改变内部文本，因为代码中的缩进、引号和特殊符号往往具有语义。对于自动文档处理器而言，比较稳妥的方法是先识别 fenced code block，在处理正文格式时暂时把代码块保护起来，正文清洗完成后再恢复代码块。这样可以避免“修复 Markdown”时意外修改代码。

例如下面的伪代码展示一个简单的幂等写入流程：

```text
load latest branch head
resolve target path
if file exists:
    fetch current blob sha
    update file with expected sha
else:
    create file
record resulting commit sha
trigger or observe build
record deployment status
```

## 20. 长文本压力段落 K

文件命名也是批量发布系统的重要组成部分。一个好的 slug 应当稳定、可读、尽量短，并避免路径保留字符。中文标题可以直接使用中文文件名，也可以转换为拼音或英文 slug；如果系统面向公开网络，通常英文和数字组成的 slug 更便于分享和兼容。为了避免标题相同导致冲突，可以在 slug 后追加任务 ID 或消息 ID 的短片段。

不过稳定性通常比“漂亮”更重要。一旦某个页面已经公开并被搜索引擎收录，频繁改变 slug 会导致链接失效。因此自动发布系统最好把最终 slug 写回数据库，并在后续更新中复用，而不是每次重新生成。

## 21. 长文本压力段落 L

对于多层任务结构，例如 task、event、act、message，可以把这些层级直接映射到目录，也可以只在数据库中保留关系、在文档站中采用更适合阅读的章节结构。目录结构过深会导致 URL 过长，也会增加导航维护成本；目录结构过浅则可能导致大量文件堆在同一层。比较常见的折中方式是以任务为顶层目录，以最终可阅读文档为页面，而把更细粒度的中间数据保留在数据库或对象存储中。

如果需要下载整个任务，可以在任务完成后生成 ZIP，把对应 Markdown、PDF 和附件放入统一目录结构。ZIP 属于构建产物，不一定需要进入 Git，可以直接上传 Blob，并把下载 URL 写回数据库。

## 22. 长文本压力段落 M

可靠发布还需要考虑取消和重试。如果任务在生成 Markdown 后被取消，就不应该继续推送；如果已经推送但还未构建，则可以根据业务需求决定是否保留提交。对于重试，应该根据失败阶段选择动作。例如 GitHub 写入已经成功而部署失败时，通常没有必要重新创建同一个文件，只需要重新触发部署或重新运行构建。

为了支持这种精确恢复，工作流最好持久化 checkpoint。checkpoint 至少应包含当前阶段、目标仓库、分支、文件路径、最后成功提交 SHA 和对应的构建信息。这样即使 worker 重启，也能从明确的位置继续，而不是从头猜测。

## 23. 长文本压力段落 N

当文档内容来自 AI 时，还可以增加发布前校验。最基础的校验包括：Frontmatter 是否存在、title 是否为空、代码围栏是否成对、常见公式标记是否闭合、文件是否超过预设大小、是否包含禁止写入的绝对路径或敏感信息。对于严格站点，还可以在提交前本地运行 Markdown parser 或 MDX compiler，尽可能把语法错误挡在 GitHub 之前。

但自动校验也不能过度修改内容。校验和格式化应该尽量可预测，并且对原始文本做最小必要变换。特别是数学公式、代码、引用和表格，错误的“智能修复”往往比不修复更危险。

## 24. 长文本压力段落 O

如果一次需要导入几十甚至几百篇 Markdown，建议先建立一个批次概念。批次记录输入压缩包、文件总数、成功数、失败数、目标分支和最终 commit。所有文件先写入临时分支，完成后运行一次整体构建。只有全部检查通过才进入生产分支。这样可以把批量导入变成一个可审查、可回滚的事务式过程。

如果部分文件失败，也可以保留失败清单，而不是让整个批次状态模糊。用户能够看到具体哪个文件失败、原因是什么、是否可以重试，会比简单显示“上传失败”更有价值。

## 25. 长文本压力段落 P

GitHub Contents API 对单个文本文件的创建和更新非常适合这种测试，因为它能够直接在指定分支创建提交。写入成功后返回提交 SHA，再通过读取同一路径和分支即可验证最终内容。相比只看 API 返回成功，重新读取是更可靠的确认方式，因为它证明远端引用确实已经指向包含目标文件的新提交。

进一步还可以比较 `main...test-branch`，确认差异只包含预期文件和导航修改。如果出现其他文件差异，就说明测试分支基线或写入步骤存在问题。

## 26. 长文本压力段落 Q

一个完整的自动发布系统最好把“测试环境”作为长期能力，而不是一次性脚本。以后任何文档格式升级、Fumadocs 版本升级、搜索索引方案修改、数学插件修改、部署平台迁移，都可以先在测试分支推一组代表性文档。代表性文档应覆盖中文、英文、长标题、表格、代码、公式、图片、超长正文和特殊字符。

本文件正是这种代表性测试文档的简化版本。虽然内容本身没有业务价值，但它覆盖了足够多的 Markdown 元素，能够帮助验证从 ChatGPT 到 GitHub 再到 Fumadocs 的基础链路。

## 27. 长文本压力段落 R

未来如果要把用户上传的 ZIP 自动导入仓库，还需要注意 ZIP Slip 路径穿越风险。解压时不能盲目信任压缩包里的文件路径，例如 `../../something` 之类的路径必须拒绝。也应当限制单个文件大小、总解压大小和文件数量，防止异常压缩包消耗过多资源。只允许预期扩展名进入文档目录，例如 `.md`、`.mdx` 和必要的图片资源。

对于 Windows 创建的压缩包，还要兼顾反斜杠路径、编码和隐藏文件。最终进入 Git 仓库的路径应统一使用 `/`，文本统一保存为 UTF-8，换行风格则可以由 Git 和格式化工具统一处理。

## 28. 长文本压力段落 S

站点构建阶段还应验证内部链接。如果批量导入时修改了文件名或目录，原 Markdown 中的相对链接可能失效。可以在构建前扫描 `[text](relative-path)` 形式的内部链接，检查目标是否存在。图片链接也一样，如果图片被迁移到对象存储，需要同步重写 Markdown 中的 URL。

对于外部链接，则不适合每次构建都完整联网检查，否则会显著拖慢构建。可以把外链检查做成异步的质量任务，而不是发布硬阻塞条件。

## 29. 长文本压力段落 T

搜索也是 Fumadocs 文档站的重要功能。长文档虽然能正常渲染，但搜索索引可能因为构建方式、预渲染限制或平台超时而失败。如果项目采用构建前生成静态搜索索引的方案，那么新增文档之后应确认索引生成器能够扫描到该文件，并把标题和正文关键字加入索引。

因此最终的端到端测试不仅应该验证 Git 文件存在，还应该验证构建产物中的搜索索引包含页面。不过本次测试首先聚焦在 GitHub 写入和分支隔离，这是最基础的一层。

## 30. 长文本压力段落 U

部署平台如果支持按分支生成预览环境，会非常适合自动化审核。每次批量文档导入都可以创建一个分支，平台自动部署，系统把预览地址反馈给用户。用户确认后，再通过 Pull Request 或自动合并进入 `main`。如果不需要人工审核，也可以在 CI 全部通过后自动合并。

这种模式的优点是生产分支始终保持可构建状态，而且任何错误都可以在合并前发现。缺点是分支和预览环境会增多，因此需要设置自动清理策略，例如导入完成并合并后删除测试分支和对应预览。

## 31. 长文本压力段落 V

对于非常大的知识库，单仓库方案最终可能遇到构建时间和索引时间增长的问题，但在规模还不大的阶段，Git 驱动文档仍然是非常简单可靠的方案。它天然提供版本历史、审查、回滚、分支和 CI 集成，特别适合结构化的技术文档和学习资料。

随着规模增长，可以再逐步把搜索、图片、PDF、下载包等重资源独立出去，而不必一开始就把整个系统复杂化。

## 32. 长文本压力段落 W

本测试还有一个目的：确认较长请求体通过连接器时不会因为中文字符、反斜杠或 Markdown 特殊符号而被破坏。特别是 LaTeX 中包含大量 `\`，JSON 又需要转义，因此实际传输链路要正确处理多层编码。最终重新读取远端文件时，如果标题、公式、代码块和末尾标记都完整，就说明基础文本编码链路正常。

因此文件最后会放置一个明确的结束标记，用于确认没有被截断。

## 33. 额外内容：网络与恢复

网络不稳定时，自动发布系统不应简单重复全部步骤，而应依赖可恢复状态。如果创建分支成功但写文件请求超时，下一次重试前应先检查文件是否已经存在。如果文件存在并且内容哈希一致，就可以认为上一次写入实际成功，只是响应丢失。如果直接再次调用“创建文件”，反而可能因为文件已经存在而失败。

同理，如果更新文件时使用 GitHub blob SHA 作为乐观并发控制，就能避免覆盖其他提交。若 SHA 不匹配，应重新读取最新内容、合并必要修改后再尝试更新，而不是强制覆盖。

## 34. 额外内容：可观察性

自动化工作流应记录结构化日志，而不是只输出自由文本。建议至少记录 `taskId`、`messageId`、`repository`、`branch`、`path`、`commitSha`、`stage`、`attempt` 和错误代码。这样发生问题后，可以按任务快速串起完整链路。

对于批量任务，还可以记录每个文件的输入哈希和输出哈希。这样既能做幂等判断，也能证明发布后的文件与输入处理结果一致。

## 35. 额外内容：安全边界

任何能够向 GitHub 写入的自动化都应该坚持最小权限。测试环境只需要对目标仓库有内容写权限，不应拥有与任务无关的组织管理权限。写入路径也应在应用层限制到指定文档目录，避免因为错误参数覆盖工作流、配置、密钥样例或应用源码。

如果未来让外部用户上传 ZIP，更应该在进入 GitHub 前做严格验证。外部输入不应直接决定目标分支、仓库或任意文件路径，这些应由服务端根据业务规则生成。

## 36. 额外内容：提交粒度

一次批量文档导入可以使用一个提交，这样审查和回滚非常直观。若需要在同一批次中逐步处理，也可以先在工作分支中产生多个提交，最后 squash 成一个提交再合并。Git 历史是否需要保留每个自动化步骤，应根据后续排错和审计需求决定。

对于普通知识库，推荐让提交信息描述业务动作，例如 `docs: import task 1234`，而不是记录底层实现细节。

## 37. 额外内容：构建验证

一个理想的测试分支验证流程可能包括：

- 检查 Markdown 文件存在。
- 检查 meta.json 已包含页面。
- 运行 lint。
- 运行 TypeScript 检查。
- 运行完整生产构建。
- 检查生成页面路径。
- 检查搜索索引。
- 检查部署预览状态。

如果以上步骤全部通过，才说明“从文档输入到可访问页面”的端到端链路真正稳定。

## 38. 额外内容：回滚策略

如果生产合并后发现问题，Git 的优势在于可以明确 revert 对应提交。相比直接在服务器文件系统上覆盖文件，Git 回滚更加透明，而且不会丢失历史。如果问题只存在于单篇文档，可以单独修复；如果整个批量导入错误，可以整体 revert。

因此自动发布时务必保存最终 commit SHA，这个 SHA 不只是日志信息，也是后续回滚和审计的重要锚点。

## 39. 额外内容：最终校验

本文件从 Frontmatter 开始，经过标题、段落、列表、引用、表格、数学公式、JavaScript、TypeScript、JSON、纯文本代码块以及大量中文长段落。如果远端读取时这些内容仍然存在，并且文件尾部的结束标记可见，就说明文本没有明显截断。

同时，如果比较测试分支与 `main` 时只出现本测试文件和测试导航配置的变化，就说明测试隔离符合预期。
