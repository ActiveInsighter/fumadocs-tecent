<Callout type="idea" title="文件定位">

该脚本与生产探活脚本逻辑近似，但它属于测试流水线。它解决 Docker Compose 或 CI 中“测试进程已经启动，数据库仍在初始化”的竞态问题。

</Callout>

## 这个文件负责什么

- 在测试套件开始前确认数据库连接可用。
- 复用生产配置中的数据库引擎，保持环境一致。
- 记录重试日志，区分应用测试失败与基础设施未就绪。
- 成功后把控制权交给 `tests-start.sh` 中的 Pytest。

## 执行思路

1. 测试容器运行 `tests-start.sh`。
2. 本脚本每秒执行一次 `SELECT 1`。
3. 连接失败时由 Tenacity 重试。
4. 连接成功后正常退出，随后执行覆盖率测试。

## 与其他模块的关系

| 模块 | 关系 |
| --- | --- |
| `backend/scripts/tests-start.sh` | 调用本脚本后启动测试。 |
| `app/core/db.py` | 提供测试所连接的数据库引擎。 |
| `backend_pre_start.py` | 生产启动链中的同类探活脚本。 |

## 与生产探活脚本的区别

<Tabs items={['共同点', '测试侧重点']}>
  <Tab>
    两者都使用同一数据库引擎、`Session`、`SELECT 1` 与 Tenacity 固定间隔重试。
  </Tab>
  <Tab>
    本脚本只为测试套件消除启动竞态；成功后不会执行迁移或写入初始数据，而是交给测试编排脚本继续处理。
  </Tab>
</Tabs>

## 带注释源码

> 原始路径：`backend/app/tests_pre_start.py`。以下只补充学习性注释与高亮标记，不改变原始执行逻辑。

```python title="tests_pre_start.py" lineNumbers
import logging

from sqlalchemy import Engine
from sqlmodel import Session, select
from tenacity import after_log, before_log, retry, stop_after_attempt, wait_fixed

from app.core.db import engine

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# 测试环境也可能比数据库更早启动，因此保留与后端一致的等待窗口。
max_tries = 60 * 5  # 5 minutes
wait_seconds = 1


@retry(
    stop=stop_after_attempt(max_tries),
    wait=wait_fixed(wait_seconds),
    before=before_log(logger, logging.INFO),
    after=after_log(logger, logging.WARN),
)
def init(db_engine: Engine) -> None:
    """等待测试数据库接受最小查询。"""
    try:
        # 只验证连接层，不要求测试表已经存在。
        with Session(db_engine) as session:
            session.exec(select(1))  # [!code highlight]
    except Exception as e:
        # 必须抛出异常，Tenacity 才会进入下一次尝试。
        logger.error(e)
        raise e


def main() -> None:
    """测试启动入口：数据库就绪后才交给 Pytest。"""
    logger.info("Initializing service")
    init(engine)
    logger.info("Service finished initializing")


if __name__ == "__main__":
    main()
```

## 阅读重点

- 探活失败应让测试任务直接失败，而不是继续产生大量误导性用例错误。
- 测试数据库应与生产数据隔离，不能仅依靠清理 fixture 保护生产库。
- 本文件和生产探活逻辑重复，实际项目可进一步提取公共函数。
