## 如何组织

| 类别 | 工作流 | 目标 |
| --- | --- | --- |
| 项目协作 | add-to-project, issue-manager, labeler | 自动管理 Issue/PR |
| 发布部署 | deploy-production, deploy-staging, latest-changes | 环境部署与变更记录 |
| 质量验证 | playwright, pre-commit, test-backend, test-docker-compose | 浏览器、静态和集成测试 |
| 依赖维护 | bump-pre-commit-hooks, guard-dependencies | 更新并约束依赖 |
| 仓库健康 | detect-conflicts, smokeshow, zizmor | 冲突、覆盖率和 Actions 安全 |

<Callout type="warn" title="权限最小化">

Actions 的 `permissions`、环境 secrets 和第三方 action 固定版本都是安全边界。工作流能写仓库或部署生产时，必须只授予所需权限。

</Callout>

## 组织原则

- 一个工作流聚焦一个清晰责任。
- 触发器限制到必要分支、路径或事件。
- 权限采用最小授权。
- 部署使用 GitHub Environments 区分 staging/production。
- 依赖 action 固定到可信版本或 commit。
- 测试工作流复用项目脚本，避免 CI 与本地命令分叉。
