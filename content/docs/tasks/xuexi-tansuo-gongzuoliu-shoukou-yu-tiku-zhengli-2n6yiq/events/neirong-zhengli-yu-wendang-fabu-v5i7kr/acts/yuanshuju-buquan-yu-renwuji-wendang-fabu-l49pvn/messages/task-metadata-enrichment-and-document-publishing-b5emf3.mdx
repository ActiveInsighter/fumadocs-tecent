---
title: "将工作流拆分为元数据补全与任务级文档发布"
description: "建议将现有工作流拆分为两个任务级流程：任务完成后统一补全 Task、Event、Act、Message 的标题、slug、摘要和标签；元数据就绪后创建发布任务，冻结快照并发布到 Fumadocs。MDX 必须生成，Markdown 与 PDF 作为可选产物，可分别或同时构建，并通过 Blob 与单次 GitHub 提交完成发布。"
---

可以，而且我认为你现在正好应该这么拆。当前工作流的根本问题不是“61 个节点太多”，而是它把 **元数据补全、单消息文档构建、PDF 任务、Blob、GitHub 发布、状态收尾**全塞在了同一个 message 级执行里。现在入口本身就是按 `messageRecordId` 读取单条消息，再生成 `content/docs/&lt;slug&gt;-&lt;messageId后8位&gt;.mdx`。

我建议彻底改成两个**任务级工作流**。

# 一、最终架构

```text
AnyWorkflow
   │
   │ task 完成
   ▼
┌────────────────────────────────────┐
│ Workflow 1                          │
│ Task Metadata Enrichment            │
│ 自动补全 / 命名                     │
└────────────────────────────────────┘
   │
   │ 读取整个 task 树
   │
   ├── Task
   │    └── Event
   │         └── Act
   │              └── Message
   │
   ├── 自动 title
   ├── slug
   ├── summary
   ├── tags
   └── publishKey
   │
   ▼
PocketBase
metadataStatus = ready
   │
   │ 创建 publish job
   ▼
┌────────────────────────────────────┐
│ Workflow 2                          │
│ Task Document Publish               │
│ 整个 Task 一次发布                  │
└────────────────────────────────────┘
   │
   ├───────────────┬───────────────────┐
   │               │                   │
   ▼               ▼                   ▼
Fumadocs MDX     Markdown Artifact    PDF Artifact
永远构建          可选                 可选
   │               │                   │
   │               │          并发 PDF 构建
   │               │                   │
   └───────────────┴───────────────────┘
                   │
                   ▼
               Blob 上传
                   │
                   ▼
          GitHub 单次 Task Commit
                   │
                   ▼
             PocketBase
       publishJob = published
```

最核心的变化是：

> **message 不再是发布单位，task 才是发布单位。**

# 二、工作流 1：自动补全信息

我建议命名：

```text
AnyWorkflow Task Metadata Enrichment
```

它只负责一件事：

> Task 完成后，对这个 Task 下所有 Task / Event / Act / Message 做结构化元数据补全。

触发条件不要再是：

```text
message created
```

而应该是：

```text
task.status → completed
```

最好由 AnyWorkflow 后端在确认整个任务完成后调用：

```text
POST /webhook/anyworkflow-task-enrich
```

只传：

```json
{
  "taskId": "...",
  "ownerId": "...",
  "checksum": "..."
}
```

然后 n8n 自己从 PocketBase 重新读取完整树：

```text
Task
│
├─ Event 1
│   ├─ Act 1
│   │   ├─ Message 1
│   │   ├─ Message 2
│   │   └─ Message 3
│   │
│   └─ Act 2
│
└─ Event 2
```

### 推荐补全的数据

| 层级      | 自动补全                                       |
| ------- | ------------------------------------------ |
| Task    | title / slug / summary / tags / publishKey |
| Event   | title / slug / summary / publishKey        |
| Act     | title / slug / summary / publishKey        |
| Message | title / slug / summary / tags / publishKey |

这里我特别建议增加：

```text
publishKey
```

不要直接拿 AI 每次生成的 slug 当永久路径。

例如：

```text
title:
TCP 三次握手详解

slug:
tcp-three-way-handshake

id:
7s8f39ab12cd456

publishKey:
tcp-three-way-handshake-12cd456
```

第一次生成以后：

```text
publishKey 永久不变
```

哪怕以后 AI 把标题改成：

```text
深入理解 TCP 三次握手
```

页面路径仍然不变。

否则每次重新跑 metadata 都可能造成：

```text
旧 URL 消失
GitHub 旧文件残留
Blob 路径变化
Fumadocs 链接失效
```

# 三、自动命名最好采用“自下而上”

不要直接把整个 Task 所有聊天内容一次塞给 AI。

大任务很容易几十万 token。

我更建议：

```text
Message metadata
       ↓
Act metadata
       ↓
Event metadata
       ↓
Task metadata
```

也就是 Message 先根据自己真实内容生成：

```json
{
  "title": "TCP 三次握手为什么需要三次",
  "summary": "...",
  "slug": "tcp-three-way-handshake",
  "tags": ["TCP", "计算机网络"]
}
```

然后 Act 不必重新读取所有长正文。

只需要：

```text
Message 1 title + summary
Message 2 title + summary
Message 3 title + summary
```

生成 Act：

```text
Act:
TCP 连接建立机制
```

再拿 Act 摘要生成 Event。

最后生成 Task。

这样就是：

```text
正文
 ↓
Message 摘要
 ↓
Act 摘要
 ↓
Event 摘要
 ↓
Task 摘要
```

规模会稳定很多。

Message 可以有限并发，例如一次 5 个；Act 也可以并发；最后 Event、Task 汇总。

# 四、不要覆盖用户手动修改的名称

这一点最好现在就设计进去。

不要只有：

```text
title
slug
summary
```

我更推荐逻辑上区分：

```text
autoTitle
autoSlug
autoSummary
autoTags

manualTitle
manualSummary
```

最终：

```text
displayTitle =
manualTitle ?? autoTitle
```

或者简单一点：

```text
metadataMode:
auto
manual
```

用户一旦人工修改：

```text
metadataMode = manual
```

AI 后续重跑就不覆盖。

否则以后你会遇到很烦的问题：

> “我明明改过标题，为什么 Task 又执行一次之后标题又被 AI 改回去了？”

# 五、工作流 1 最后的状态

Task 建议增加：

```text
metadataStatus
```

状态：

```text
pending
   ↓
processing
   ↓
ready

或者

failed
```

只有：

```text
task.status = completed
AND
metadataStatus = ready
```

才允许进入发布流程。

这样职责非常清楚：

```text
Task 完成
≠
可以发布

Task 完成
+
metadata 补全成功
=
可以发布
```

# 六、增加一个非常重要的东西：Publish Job

第二个工作流不要只靠 `task.status` 判断。

建议新增：

```text
aw_publish_jobs
```

一个 Task 每次正式发布产生一个 Publish Job。

比如：

```json
{
  "task": "task123",
  "version": 3,

  "buildMd": true,
  "buildPdf": true,

  "sourceChecksum": "...",

  "status": "queued",

  "totalDocuments": 18,
  "completedDocuments": 0
}
```

状态：

```text
queued
  ↓
snapshotting
  ↓
building
  ↓
uploading
  ↓
committing
  ↓
published
```

错误：

```text
failed
```

于是：

```text
Task
  │
  ├── Publish Job v1
  ├── Publish Job v2
  └── Publish Job v3
```

每一次发布都有完整历史。

这比把所有状态都塞进 `aw_documents.status` 好很多。

# 七、工作流 2：Task Document Publish

建议名称：

```text
AnyWorkflow Task Document Publish
```

入口：

```json
{
  "publishJobId": "...",
  "taskId": "...",
  "buildMd": true,
  "buildPdf": true
}
```

最重要的第一步：

> **冻结 Task 快照。**

也就是这次 Publish Job 一旦开始，就确定：

```text
有哪些 Event
有哪些 Act
有哪些 Message
顺序是什么
正文是什么
metadata 是什么
checksum 是什么
```

之后即使用户数据库又改了东西，也不能让“同一次发布”前后文件内容不一致。

---

# 八、四种构建模式

这里我建议用两个 boolean，而不是搞复杂配置：

```text
buildMd
buildPdf
```

对应：

| buildMd | buildPdf | 结果                  |
| ------: | -------: | ------------------- |
|   false |    false | 只发布 Fumadocs 页面     |
|    true |    false | Fumadocs + MD       |
|   false |     true | Fumadocs + PDF      |
|    true |     true | Fumadocs + MD + PDF |

这里有一个概念要明确：

## MDX 和 MD 不是一回事

**MDX 是 Fumadocs 页面源文件，发布网站永远需要生成。**

`buildMd` 指的是：

```text
是否额外生成可下载的 .md artifact
```

所以：

```text
buildMd = false
buildPdf = false
```

不是“什么都不做”。

而是：

```text
✓ Fumadocs MDX
✗ 下载 MD
✗ 下载 PDF
```

这样设计最合理。

# 九、文件目录应该彻底变成 Task → Event → Act → Message

现在是：

```text
content/docs/<messageSlug>-<messageId>.mdx
```

比较扁平。

我推荐改成：

```text
content/docs/tasks/
└── <taskPublishKey>/
    ├── index.mdx
    ├── meta.json
    │
    └── events/
        └── <eventPublishKey>/
            ├── index.mdx
            ├── meta.json
            │
            └── acts/
                └── <actPublishKey>/
                    ├── index.mdx
                    ├── meta.json
                    │
                    └── messages/
                        ├── <message1PublishKey>.mdx
                        ├── <message2PublishKey>.mdx
                        └── <message3PublishKey>.mdx
```

例如：

```text
content/docs/tasks/
└── learn-computer-network-a83f91/
    ├── index.mdx
    │
    └── events/
        └── tcp-protocol-f182ab/
            ├── index.mdx
            │
            └── acts/
                └── tcp-connection-72da91/
                    ├── index.mdx
                    │
                    └── messages/
                        ├── tcp-handshake-93ef11.mdx
                        ├── tcp-four-way-close-a112cc.mdx
                        └── tcp-state-machine-c839a1.mdx
```

这就是真正的数据关系直接映射到文件系统。

# 十、Task / Event / Act 也值得有 index.mdx

我非常建议做。

例如 Task 首页：

```markdown
# 计算机网络学习

任务摘要……

## Events

- TCP 协议
- HTTP
- DNS
```

Event 首页：

```markdown
# TCP 协议

Event 摘要……

## Acts

- TCP 建立连接
- TCP 可靠传输
```

Act 首页：

```markdown
# TCP 建立连接

Act 摘要……

## Messages

- 为什么需要三次握手
- SYN 和 ACK 是什么
- 四次挥手
```

最后才到真实 Message：

```markdown
# 为什么 TCP 需要三次握手

<assistantMarkdown>
```

那么用户进入文档站之后真的就是：

```text
Task
 ↓
Event
 ↓
Act
 ↓
Message
```

而不是目录结构有层级、页面体验却没有层级。

# 十一、Blob 也采用完全相同的层级

不过 Blob 我更建议使用 **ID + Task 发布版本**，而不是 human slug。

因为 Blob 本质是内部存储。

例如：

```text
documents/
└── tasks/
    └── <taskId>/
        └── v3/
            └── events/
                └── <eventId>/
                    └── acts/
                        └── <actId>/
                            └── messages/
                                └── <messageId>/
                                    ├── document.md
                                    └── document.pdf
```

这样最大的好处是：

```text
Task v1
Task v2
Task v3
```

永远不会互相覆盖。

而且整个 Task 发布版本是一致的。

# 十二、PDF 要改成“批量并发”

这个地方是我认为拆分以后最大的优化点。

现在的工作流是：

```text
一条 message
 ↓
创建一个 pdf_job
 ↓
workflow_dispatch
 ↓
等 10 秒
 ↓
查询
 ↓
没完成
 ↓
再等 10 秒
```

然后循环。当前工作流确实是 `Wait → Get Job → Ready? → 不 Ready 再 Wait`。

如果一个 Task 有：

```text
30 条 message
```

千万不要在一个 n8n 流程里：

```text
PDF1 完成
再 PDF2
再 PDF3
...
```

那会非常慢。

应该变成：

```text
30 Message
     │
     ▼
同时创建 30 个 pdf_jobs
     │
     ▼
同时上传 input.md
     │
     ▼
一个 Batch Dispatch
     │
     ▼
GitHub Actions
Matrix
┌────┬────┬────┬────┐
PDF1 PDF2 PDF3 ... PDF30
└────┴────┴────┴────┘
     │
     ▼
n8n 查询整个 batch
```

推荐给 `pdf_jobs` 增加：

```text
publish_job_id
task_id
document_id
```

于是：

```sql
publish_job_id = xxx
```

一次就可以查询：

```text
30 个 PDF：
completed 27
building   2
failed     1
```

而不需要在 n8n 里面维护 30 条复杂循环。

# 十三、最好只 Dispatch 一次 GitHub Action

当前是一篇文档对应一个 PDF Action。

新设计可以做：

```text
build-pdf-batch.yml
```

n8n：

```text
生成全部 pdf_jobs
       ↓
上传全部 input.md
       ↓
status = queued
       ↓
workflow_dispatch

publish_job_id = xxx
```

GitHub Action：

```text
读取 publish_job_id
      ↓
取得全部 queued jobs
      ↓
matrix
 ┌────┬────┬────┐
 job1 job2 job3 ...
 └────┴────┴────┘
      ↓
分别输出 PDF
```

这会比 n8n Dispatch 30 次漂亮很多。

# 十四、MD 和 PDF 并行

第二个工作流内部可以变成：

```text
               Task Snapshot
                    │
          ┌─────────┼──────────┐
          │         │          │
          ▼         ▼          ▼
        MDX       MD分支      PDF分支
      mandatory   optional    optional
          │         │          │
          │         │       GitHub Matrix
          │         │          │
          └─────────┼──────────┘
                    ▼
               Wait All
                    │
                    ▼
               Publish
```

例如：

```text
buildMd=true
buildPdf=true
```

就：

```text
MD 上传 Blob
       ↘
         同时进行
       ↗
PDF 构建
```

没必要等 MD 上传完才开始 PDF。

# 十五、GitHub 发布也应该从“逐文件提交”改掉

这个非常重要。

你现在的工作流是：

```text
GET GitHub file
 ↓
PUT 一个 MDX
 ↓
GET meta.json
 ↓
PUT meta.json
```

也就是文件级 Contents API，一篇文档至少多个 GitHub 操作。

如果一个 Task 有：

```text
30 messages
10 acts
4 events
```

新结构可能一下产生：

```text
30 message.mdx
10 act/index.mdx
4 event/index.mdx
1 task/index.mdx
十几个 meta.json
```

如果一个个 PUT：

```text
可能产生五六十次 commit
```

这非常不好。

## 应该改成一个 Task = 一个 Git Commit

通过 GitHub Git Data API：

```text
读取 main HEAD
      ↓
读取 base tree
      ↓
创建所有 blob
      ↓
一次 Create Tree
      ↓
一次 Create Commit
      ↓
Update Ref
```

最终 GitHub：

```text
commit:

docs: publish task <taskPublishKey>

包含：
56 个文件修改
```

一次提交全部生效。

这才真正符合：

> **“直接把一个任务里的内容全发布。”**

# 十六、这样可以得到近似“原子发布”

整个顺序我建议：

```text
冻结 Task Snapshot
       ↓
构建所有 MDX
       ↓
创建所有 PDF jobs
       ↓
   ┌── MD 上传 Blob
   │
   └── PDF 并行生成 + 上传 Blob
       ↓
所有 artifact 准备完毕
       ↓
生成整个 Git tree
       ↓
GitHub 一个 commit
       ↓
PocketBase:
Publish Job → published
Documents   → published
Artifacts   → published
```

这里 Blob 文件可能已经提前上传，但在：

```text
Publish Job != published
```

之前不要向用户暴露下载。

因此即便出现：

```text
Blob 成功
GitHub commit 失败
```

用户也看不到半发布状态。

重新跑 Publish Job 可以直接复用已经成功的 Blob artifact。

# 十八、两个工作流之间不要强耦合

我推荐：

```text
Workflow 1
Metadata Enrichment
       ↓
metadataStatus = ready
       ↓
创建 aw_publish_jobs
status = queued
       ↓
调用 Workflow 2
```

而不是 Workflow 1 直接接着几十个发布节点。

这样 Workflow 2 可以单独重跑。

比如 PDF 出问题：

```text
Metadata Workflow
✓ 已经成功

Publish Workflow
✗ PDF Action 失败
```

只需要：

```text
Retry publishJob
```

而不需要再调用 AI 重新生成 Task / Event / Act / Message 名称。

# 十九、最终两个工作流会非常清楚

### Workflow A

```text
AnyWorkflow Task Metadata Enrichment

Task Completed
      ↓
验证
      ↓
读取 Task 完整树
      ↓
锁定 metadata processing
      ↓
Message metadata 并发
      ↓
Act metadata
      ↓
Event metadata
      ↓
Task metadata
      ↓
写 PocketBase
      ↓
metadataStatus = ready
      ↓
创建 Publish Job
      ↓
触发 Workflow B
```

### Workflow B

```text
AnyWorkflow Task Document Publish

Publish Job
      ↓
读取 Task 完整树
      ↓
冻结 Snapshot
      ↓
生成 Task/Event/Act/Message MDX
      ↓
      ┌──────────────────────┐
      │                      │
 buildMd?                 buildPdf?
      │                      │
      ▼                      ▼
上传 MD                 批量 PDF Jobs
                             ↓
                      GitHub Matrix
                             ↓
                          上传 PDF
      │                      │
      └──────────┬───────────┘
                 ↓
             All Ready
                 ↓
       GitHub 单次 Tree Commit
                 ↓
       更新 PocketBase 状态
                 ↓
             published
```

## 我最推荐你现在采用的几个原则

1. **Task 是发布事务边界，不再是 Message。**
2. **元数据工作流和发布工作流完全拆开。**
3. **Task 完成后再统一补全 Task/Event/Act/Message。**
4. **MDX 永远生成；MD、PDF 是两个独立可选 artifact。**
5. **PDF 按整个 Task 批量建立 job，并发构建。**
6. **GitHub 一个 Task 只产生一次 commit。**
7. **GitHub 路径按 Task → Event → Act → Message 组织。**
8. **Blob 按 Task 发布版本 + ID 层级存储。**
9. **AI slug 不直接当永久路径，第一次生成 `publishKey` 后冻结。**
10. **增加 `aw_publish_jobs`，把一次任务发布真正变成一个可追踪、可重试的批次。**

这样改完以后，现在那个 61 节点大工作流就不是简单“砍成两半”，而是从**message 驱动的流水线**真正升级成了**Task 级文档发布系统**。这会更适合你现在 AnyWorkflow 的 `Task → Event → Act → Message` 数据模型，而且未来想加 HTML、DOCX、ZIP、整 Task PDF 等格式，也只是在 Publish Job 里再增加 artifact 类型，不需要再重构整个架构。
