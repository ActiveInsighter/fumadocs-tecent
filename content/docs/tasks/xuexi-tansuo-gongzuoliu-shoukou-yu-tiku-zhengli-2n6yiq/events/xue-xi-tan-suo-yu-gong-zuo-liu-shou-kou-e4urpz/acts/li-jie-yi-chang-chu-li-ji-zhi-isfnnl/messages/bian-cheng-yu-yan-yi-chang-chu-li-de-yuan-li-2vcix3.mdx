---
title: "编程语言异常处理的原理"
description: "异常处理是一种非局部控制流机制。当程序通过 throw 或 raise 抛出异常时，运行时会沿调用栈向上搜索匹配的处理器，并在栈展开过程中执行资源清理，最终将控制权交给 catch 或 except。不同语言在资源管理、错误传播和异常类型设计上各有差异。"
---

编程语言里的**异常处理（exception handling）**，本质上是在解决一个问题：

> **程序执行到某一步发现“正常流程没法继续了”，怎样把错误信息安全地传递给上层，并自动执行必要的清理工作。**

它和操作系统里的“异常/中断”不是同一个概念。编程语言异常通常是**语言和运行时提供的一套控制流机制**，不过有些异常最终确实可能由 CPU/操作系统异常触发。

你可以先把它理解成一种“特殊的、可以跨很多层函数返回的控制流”。

---

# 一、先看最普通的错误处理

假设有：

```text
main()
  ↓
login()
  ↓
readUser()
  ↓
readDatabase()
```

最底层 `readDatabase()` 发现数据库连接失败。

不用异常的话，通常只能：

```cpp
int readDatabase() {
    if (连接失败) {
        return -1;
    }

    return 0;
}
```

然后调用者必须不停检查：

```cpp
int readUser() {
    int result = readDatabase();

    if (result == -1) {
        return -1;
    }

    return 0;
}
```

上一层：

```cpp
int login() {
    int result = readUser();

    if (result == -1) {
        return -1;
    }

    return 0;
}
```

再上一层：

```cpp
int main() {
    int result = login();

    if (result == -1) {
        cout << "数据库错误";
    }
}
```

问题非常明显：

```text
readDatabase
    ↓ 返回错误码
readUser
    ↓ 返回错误码
login
    ↓ 返回错误码
main
```

中间这些函数其实根本不知道怎么处理数据库错误，却必须一层一层“转发”。

这就是异常机制要解决的问题。

# 二、异常的核心思想

异常处理让底层函数可以直接：

```cpp
throw DatabaseException();
```

然后程序运行时自动寻找上层有没有：

```cpp
try {
    ...
}
catch (DatabaseException& e) {
    ...
}
```

于是整个过程变成：

```text
main()
└── try
    └── login()
        └── readUser()
            └── readDatabase()
                  ↓
                 throw
                  ↓
            自动跳过
        自动跳过
    自动跳过
        ↓
catch 捕获
```

这就是异常最核心的原理：

> **throw 抛出异常后，程序不再按照正常函数返回路径执行，而是沿调用栈向上寻找匹配的异常处理器 catch。**

这个过程叫：

> **Stack Unwinding**
>
> 栈展开 / 调用栈展开

这是理解异常最重要的词。

# 三、try / throw / catch 到底分别干什么

以 C++ 为例：

```cpp
try {
    int result = divide(10, 0);
}
catch (const std::exception& e) {
    std::cout << e.what();
}
```

底层：

```cpp
int divide(int a, int b) {
    if (b == 0) {
        throw std::runtime_error("除数不能为 0");
    }

    return a / b;
}
```

三个关键字：

```text
try
↓
“这里面的代码可能出异常”

throw
↓
“发生异常，停止正常执行，开始寻找处理器”

catch
↓
“如果这种异常来到这里，我负责处理”
```

运行过程：

```text
try
 │
 ▼
divide(10, 0)
 │
 ▼
b == 0
 │
 ▼
throw runtime_error
 │
 ▼
divide() 不再正常 return
 │
 ▼
寻找 catch
 │
 ▼
catch(runtime_error / exception)
 │
 ▼
执行异常处理代码
```

# 四、最关键的底层概念：调用栈

异常之所以能够“跨好几层函数”，依赖的是**调用栈**。

比如：

```cpp
void C() {
    throw Error();
}

void B() {
    C();
}

void A() {
    B();
}

int main() {
    try {
        A();
    }
    catch (...) {
        ...
    }
}
```

执行到 `C()` 时，运行栈大概是：

```text
高地址

┌───────────────┐
│ C 栈帧        │ ← 当前
├───────────────┤
│ B 栈帧        │
├───────────────┤
│ A 栈帧        │
├───────────────┤
│ main 栈帧     │
└───────────────┘

低地址
```

`C()` 执行：

```cpp
throw Error();
```

运行时首先检查：

```text
C 有没有能捕获 Error 的 catch？
```

没有。

于是：

```text
销毁 C 栈帧
```

继续看 B。

```text
┌───────────────┐
│ B 栈帧        │ ← 当前
├───────────────┤
│ A 栈帧        │
├───────────────┤
│ main 栈帧     │
└───────────────┘
```

B 也没有。

继续展开：

```text
┌───────────────┐
│ A 栈帧        │ ← 当前
├───────────────┤
│ main 栈帧     │
└───────────────┘
```

A 也没有。

最后来到 main：

```cpp
catch (...) {
}
```

匹配成功。

于是跳进去执行。

所以异常非常像：

```text
throw
=
“我要沿着调用栈疯狂向上 return，
直到找到愿意处理我的人。”
```

但是它比普通 `return` 强得多，因为运行时会自动完成这个过程。

# 五、为什么叫“栈展开”

因为原来的栈：

```text
C
B
A
main
```

异常发生后依次：

```text
弹出 C
弹出 B
弹出 A
```

最后留下：

```text
main
```

所以叫：

```text
stack unwinding
```

即：

> 把调用栈一层一层拆掉。

但这里有一个特别重要的问题：

> 被拆掉的函数里面如果有局部资源怎么办？

比如：

```cpp
void B() {
    File file("test.txt");

    C();
}
```

如果 `C()` 抛异常，`B()` 直接被跳过：

```text
那 file 怎么办？
```

这就涉及异常机制的第二个核心功能：

> **资源清理。**

# 六、异常真正困难的地方不是“跳转”，而是“清理”

假设：

```cpp
void test() {
    Object a;
    Object b;

    riskyFunction();

    Object c;
}
```

如果 `riskyFunction()` 抛异常：

```text
a 已创建
b 已创建
riskyFunction 出异常
c 还没创建
```

运行时不能简单地：

```text
jmp catch
```

否则：

```text
a、b 没析构
文件没关闭
锁没释放
内存没释放
```

就出问题了。

因此 C++ 在栈展开过程中会自动执行析构函数：

```text
创建顺序：

a
↓
b

异常发生

析构顺序：

b
↓
a
```

例如：

```cpp
class Test {
public:
    Test(const char* name) : name(name) {
        cout << "create " << name << endl;
    }

    ~Test() {
        cout << "destroy " << name << endl;
    }

private:
    const char* name;
};
```

然后：

```cpp
void f() {
    Test a("A");
    Test b("B");

    throw std::runtime_error("error");
}
```

会出现：

```text
create A
create B

异常

destroy B
destroy A
```

这就是为什么 C++ 特别强调：

> **RAII**

Resource Acquisition Is Initialization。

例如：

```cpp
std::lock_guard<std::mutex> lock(mutex);
```

即使后面：

```cpp
throw
```

`lock` 的析构函数也会执行，于是自动解锁。

# 七、Java / Python 怎么做资源清理？

不同语言设计不一样。

## Java

Java 有：

```java
try {
    ...
}
catch (Exception e) {
    ...
}
finally {
    ...
}
```

`finally` 基本含义：

> 不管有没有异常，都执行。

比如：

```java
FileInputStream file = null;

try {
    file = new FileInputStream("a.txt");
}
catch (IOException e) {
    ...
}
finally {
    if (file != null) {
        file.close();
    }
}
```

现在更常见的是：

```java
try (FileInputStream file =
         new FileInputStream("a.txt")) {

    ...
}
```

这叫：

```text
try-with-resources
```

思想和 C++ RAII 很类似。

---

## Python

Python：

```python
try:
    ...
except ValueError:
    ...
finally:
    ...
```

还有：

```python
with open("a.txt") as f:
    ...
```

`with` 会保证退出时调用清理逻辑。

也就是说：

```text
C++       RAII / destructor
Java      finally / try-with-resources
Python    finally / with
```

底层目标都是一样：

> 出异常也不能把资源弄丢。

# 八、异常对象是什么？

你可以把异常理解成一个特殊对象。

比如：

```cpp
throw std::runtime_error("file not found");
```

这里实际上创建了一个：

```cpp
std::runtime_error
```

对象，其中保存：

```text
异常类型
异常信息
可能还有其他字段
```

Java：

```java
throw new IOException("文件不存在");
```

Python：

```python
raise ValueError("参数错误")
```

本质都是：

```text
创建异常对象
        ↓
把异常对象交给异常处理机制
        ↓
沿栈向上寻找合适的 handler
```

# 九、catch 是怎么匹配异常类型的？

比如：

```cpp
try {
    ...
}
catch (const FileException& e) {
}
catch (const NetworkException& e) {
}
catch (const std::exception& e) {
}
catch (...) {
}
```

运行时会根据异常类型寻找合适的处理器。

假如：

```cpp
throw FileException();
```

那么：

```text
FileException
      ↓
catch(FileException)
```

优先匹配。

如果没有：

```text
FileException
    ↓
std::exception
```

如果它继承自 `std::exception`，可能匹配：

```cpp
catch(const std::exception& e)
```

最后：

```cpp
catch (...)
```

类似：

```text
任何异常我都接住
```

Java 也是类似继承体系：

```text
Throwable
├── Error
└── Exception
    └── RuntimeException
```

例如：

```java
try {
}
catch (FileNotFoundException e) {
}
catch (IOException e) {
}
catch (Exception e) {
}
```

必须一般来说：

```text
具体异常
↓
一般异常
```

不能反过来。

# 十、如果一直没人 catch 怎么办？

例如：

```cpp
void C() {
    throw Error();
}

void B() {
    C();
}

void A() {
    B();
}

int main() {
    A();
}
```

整个调用链：

```text
C
↓
B
↓
A
↓
main
↓
仍然没人处理
```

那么通常程序就会异常终止。

C++：

```text
std::terminate()
```

Java：

```text
线程终止
打印 stack trace
```

Python：

```text
Traceback
...
ValueError: ...
```

你经常看到 Python：

```text
Traceback (most recent call last):
  File "main.py", line 10, in <module>
    a()
  File "main.py", line 7, in a
    b()
  File "main.py", line 4, in b
    raise ValueError("error")

ValueError: error
```

其实这个 Traceback 就是在把：

```text
main → a → b
```

这一整条调用栈展示给你。

# 十一、异常和 return 最大区别

普通 `return`：

```cpp
return -1;
```

只能返回给：

> **直接调用者。**

假设：

```text
A → B → C → D
```

D：

```cpp
return -1;
```

只能先返回 C。

于是：

```text
D → C
C → B
B → A
```

每一层都得手动传。

而：

```cpp
throw Error();
```

可以：

```text
D
│
│ 没人处理
▼
C
│
│ 没人处理
▼
B
│
│ 没人处理
▼
A
│
▼
catch
```

所以：

```text
return
=
局部控制流

exception
=
非局部控制流
```

这是一个很重要的概念。

# 十二、那异常底层到底是不是 goto？

从“控制流效果”来说，可以粗略理解成：

```text
高级版 goto
```

但实际上复杂得多。

因为普通：

```cpp
goto label;
```

基本只是改变 PC：

```text
PC = label地址
```

而异常需要：

```text
1. 找异常处理器
2. 判断类型是否匹配
3. 展开调用栈
4. 销毁局部对象
5. 恢复栈指针
6. 恢复寄存器
7. 跳到 catch
```

所以异常实际上可以粗略理解为：

```text
异常 =
非局部跳转
+
调用栈搜索
+
资源清理
+
类型匹配
```

# 十三、编译器怎么实现异常？

这是最有意思的底层部分。

这里以现代 C++ 为例。

编译器编译：

```cpp
try {
    foo();
}
catch (const Error& e) {
    handle(e);
}
```

不会真的生成一个“try 指令”。

CPU 根本不知道：

```text
try
catch
throw
```

是什么。

CPU 只知道：

```text
mov
call
jmp
ret
push
pop
...
```

所以：

> **异常是编译器 + 运行时库共同实现的。**

编译器会额外生成一些：

```text
异常处理表
unwind information
landing pad
```

大致类似：

```text
代码地址范围        异常处理信息

0x1000-0x1050       handler A
0x1050-0x1080       handler B
0x1080-0x1100       none
```

当异常发生：

```text
throw
↓
异常运行时库
↓
查看当前 PC
↓
查异常表
↓
当前函数有没有对应 handler？
```

如果没有：

```text
读取 unwind information
↓
恢复调用者栈帧
↓
继续搜索
```

直到找到。

# 十四、现代 C++ 的“零成本异常”是什么？

你可能以后会看到：

> Zero-cost exception handling

这个名字很容易误解。

并不是：

> 抛异常不要成本。

而是：

> **正常不抛异常时，额外运行时成本非常低。**

比如：

```cpp
try {
    foo();
}
catch (...) {
}
```

如果 `foo()` 一切正常，大多数情况下不会每执行一步都检查：

```text
有异常吗？
有异常吗？
有异常吗？
```

而是正常直接跑。

相关异常信息存在程序的：

```text
exception table
unwind table
```

里。

只有真正发生：

```cpp
throw
```

时，才去做：

```text
查询表
栈展开
对象析构
类型匹配
```

于是：

```text
正常路径：快
异常路径：比较贵
```

这就是为什么一般建议：

> **异常适合真正的异常情况，不适合拿来当高频普通流程控制。**

例如不要写成：

```cpp
try {
    找用户
}
catch (UserNotFound) {
    // 很常见
}
```

如果“用户不存在”本来就是特别常见的正常业务分支，可以考虑：

```cpp
optional<User>
```

或者正常状态返回。

# 十五、异常和 CPU 异常是什么关系？

这里特别容易混淆。

假设：

```cpp
int x = 1 / 0;
```

可能首先发生的是 CPU 层面的：

```text
除零异常
Divide Error
```

路径可能变成：

```text
程序执行 div
↓
CPU 检测除 0
↓
CPU Exception
↓
进入操作系统内核
↓
操作系统处理
```

之后操作系统可能：

```text
Linux → SIGFPE
Windows → structured exception
```

然后语言运行时可能再进行转换。

比如某些平台：

```text
CPU Exception
      ↓
OS Exception / Signal
      ↓
Language Runtime
      ↓
Language Exception
```

但是千万不要理解成：

> 所有 `throw` 都会触发 CPU Exception。

比如：

```cpp
throw std::runtime_error("abc");
```

这是纯软件层面行为：

```text
普通机器指令
↓
调用异常运行时
↓
开始 stack unwinding
```

CPU 并没有发生硬件异常。

你之前学操作系统异常时，可以这样联系起来。

## 第一层：CPU 异常

例如：

```text
除零
缺页
非法指令
一般保护异常
```

属于：

```text
硬件 / CPU
```

## 第二层：操作系统异常机制

例如：

```text
Linux Signal

```

操作系统决定怎么通知进程。

## 第三层：编程语言异常

例如：

```text
C++:
throw / try / catch

Java:
throw / try / catch

Python:
raise / try / except
```

属于：

```text
语言运行时
```

可以画成：

但注意：

```text
语言异常
```

**不一定经过下面两层。**

# 十七、Java 为什么区分 checked 和 unchecked exception？

Java 有一个比较独特的设计。

比如：

```java
IOException
```

属于 checked exception。

如果函数：

```java
void read() throws IOException {
}
```

调用者必须：

```java
try {
    read();
}
catch (IOException e) {
}
```

或者：

```java
void foo() throws IOException {
    read();
}
```

继续向上声明。

也就是说：

> 编译器强制你处理。

而：

```java
NullPointerException
ArithmeticException
IndexOutOfBoundsException
```

属于 RuntimeException：

```text
unchecked exception
```

编译器不会强制处理。

设计思想大致是：

```text
可恢复外部错误
↓
checked

程序逻辑 bug
↓
unchecked
```

不过这个设计在编程语言界争议很大。

C++、Python、JavaScript 等都没有 Java 这种强 checked exception 机制。

# 十八、Python 的异常为什么那么常见？

Python 非常鼓励一种思想：

> EAFP

即：

```text
Easier to Ask Forgiveness than Permission
```

可以理解为：

> 先干，失败了再处理。

比如：

```python
try:
    value = dictionary[key]
except KeyError:
    value = default
```

而不是：

```python
if key in dictionary:
    value = dictionary[key]
else:
    value = default
```

所以 Python 中异常不仅用于“灾难性错误”，很多时候也用于正常 API 设计。

# 十九、Go 为什么不喜欢传统异常？

Go 是一个很有意思的反例。

Go 没有 Java/C++ 那种常规：

```text
try / catch
```

而是大量写：

```go
value, err := doSomething()

if err != nil {
    return err
}
```

例如：

```go
file, err := os.Open("a.txt")

if err != nil {
    return err
}
```

它的哲学是：

> 错误也是普通数据，应该显式处理。

所以两种哲学：

```text
C++ / Java / Python
```

# 二十、Rust 又是另一条路线

Rust 区分：

```text
可恢复错误
Result<T, E>

不可恢复错误
panic!
```

比如：

```rust
fn read() -> Result<String, Error> {
}
```

调用者：

```rust
match read() {
    Ok(value) => ...
    Err(e) => ...
}
```

或者：

```rust
let value = read()?;
```

其中：

```rust
?
```

其实非常像异常传播：

```text
如果成功
↓
拿值继续

如果失败
↓
自动 return Err(...)
```

所以 Rust：

```text
Result + ?
```

在某种意义上获得了：

```text
异常传播的便利
+
错误类型显式化
```

但没有传统异常的隐式 stack unwinding 语义作为普通错误机制。

# 二十一、异常处理最经典的代码结构

一般：

```cpp
try {
    // 正常流程
}
catch (SpecificException& e) {
    // 特定错误
}
catch (std::exception& e) {
    // 一般错误
}
catch (...) {
    // 最后兜底
}
```

可以理解为：

```text
       正常执行
           │
           ▼
     ┌────────────┐
     │    try     │
     └─────┬──────┘
           │
      有没有异常？
       /       \
      无        有
      │         │
      ▼         ▼
   继续执行    throw
                │
                ▼
          展开调用栈
                │
                ▼
          查找匹配 catch
                │
                ▼
            处理异常
```

# 二十二、一个完整例子

来看一个非常典型的：

```cpp
#include <iostream>
#include <stdexcept>

void readFile() {
    std::cout << "readFile begin\n";

    throw std::runtime_error("file does not exist");

    std::cout << "readFile end\n";
}

void parseFile() {
    std::cout << "parseFile begin\n";

    readFile();

    std::cout << "parseFile end\n";
}

void loadConfig() {
    std::cout << "loadConfig begin\n";

    parseFile();

    std::cout << "loadConfig end\n";
}

int main() {
    try {
        loadConfig();
    }
    catch (const std::exception& e) {
        std::cout << "catch: " << e.what() << '\n';
    }
}
```

输出：

```text
loadConfig begin
parseFile begin
readFile begin
catch: file does not exist
```

注意：

```text
readFile end
parseFile end
loadConfig end
```

全部没有执行。

为什么？

因为：

```text
readFile
   ↓ throw

readFile 栈展开
   ↓
parseFile 栈展开
   ↓
loadConfig 栈展开
   ↓
main 找到 catch
```

这就是异常传播。

# 二十三、异常处理其实体现了一种“职责分离”

这是异常设计最漂亮的地方。

底层：

```cpp
readFile()
```

知道：

> 文件读取失败了。

但是它可能不知道：

> 应该重试？
> 弹窗？
> 退出程序？
> 使用默认配置？

因此它只负责：

```cpp
throw FileException();
```

而高层：

```cpp
main()
```

知道业务逻辑，因此决定：

```text
重试
或
显示错误
或
降级
或
终止
```

于是：

```text
底层：
发现错误

中层：
不关心，传播

高层：
决定怎么办
```

这就是异常机制最大的设计价值。

# 二十四、最后用一句话理解异常

如果普通函数调用是：

```text
A
↓
B
↓
C
↓
D

正常返回：

D → C → B → A
```

那么异常是：

```text
A try
↓
B
↓
C
↓
D throw
↑
C 不处理，拆栈
↑
B 不处理，拆栈
↑
A catch
```

因此异常处理的本质可以浓缩成：

> **异常是一种由编译器和运行时支持的非局部控制流机制：当 `throw/raise` 发生时，运行时沿调用栈向上搜索匹配的处理器，在搜索过程中执行必要的栈展开和资源清理，最后把控制权转移给 `catch/except`。**

而你如果把它和操作系统知识连起来，可以记成这张层级图：

```text
程序正常函数控制流
        │
        ├── return
        │      └── 返回一层
        │
        └── throw
               └── 跨多层寻找 handler
                         │
                         └── stack unwinding


语言层异常
try / catch / throw
        ↑
        │ 有时由此转化
操作系统层
Signal / SEH
        ↑
        │
CPU 异常
缺页 / 除零 / 非法指令...
```

其中最值得你牢牢记住的三个词就是：

**`异常传播 → handler 搜索 → stack unwinding（栈展开）`。**

把这三个真正理解了，C++、Java、Python、JavaScript 的异常机制基本就都通了。
