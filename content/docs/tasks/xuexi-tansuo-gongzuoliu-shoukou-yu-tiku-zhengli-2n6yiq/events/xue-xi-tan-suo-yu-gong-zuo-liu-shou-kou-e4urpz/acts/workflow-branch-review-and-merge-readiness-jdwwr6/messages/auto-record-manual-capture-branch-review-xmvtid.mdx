# 1. 最大的进步：跨标签页并发问题基本修对了

上次最重要的问题之一是：

```text
Tab A ─┐
       ├→ chrome.storage.local
Tab B ─┘
```

两个 content script 各自有自己的 Promise queue，因此可能同时：

```text
read S
modify
write
```

导致 lost update。

现在你改成了：

```text
Content Script A ─┐
Content Script B ─┼─ runtime message
Content Script C ─┘
          ↓
Service Worker
          ↓
ManualHistoryGroupingHandler
          ↓
ManualHistoryGroupingStore
          ↓
chrome.storage.local
```

这是正确解法。

`AutoRecordController` 已经不再直接：

```ts
createManualHistoryGroupingStore()
```

而是：

```ts
createManualHistoryGroupingClient()
```

然后发：

```text
AW_MANUAL_HISTORY_GROUPING_ALLOCATE
```

到 background。

而 service worker 只创建一个：

```ts
const manualHistoryGroupingHandler =
  createManualHistoryGroupingRuntimeHandler({
    ...
    store: createManualHistoryGroupingStore(),
  });
```

这样模块级：

```ts
let storageQueue: Promise<void>
```

现在运行在 **service worker 单写者上下文** 中，因此它终于真的能承担全局串行化作用了。

这个改法比试图在 content script 间自己造锁要干净得多。

# 3. 第二个大问题：Checkpoint durability 这次也修得比较完整

上次有一个危险逻辑：

```text
checkpoint.save 失败
↓
只记日志
↓
继续 capture / collect
```

现在已经改成：

```ts
try {
  await this.persistCheckpoint(checkpoint);
} catch {
  ...
  return;
}
```

也就是：

```text
无法建立 durable checkpoint
        ↓
不允许进入后续执行
```

这个语义现在就对了。

并且你还显式维护：

```ts
checkpointDurable
checkpointClearPending
```

`persistCheckpoint()`：

```text
pendingCheckpoint = checkpoint
checkpointDurable = false
↓
storage.save
↓
成功
↓
checkpointDurable = true
```

保存失败则抛出，而不是吞掉。

这个变化很重要。

# 4. `clear checkpoint` 失败的行为现在也合理多了

之前危险的情况是：

```text
history 已保存
↓
checkpointStore.clear() 失败
↓
内存 pendingCheckpoint 却直接 null
```

下一次 reload 就会看到旧 checkpoint。

现在：

```ts
if clear failed:
    pendingCheckpoint = checkpoint
    checkpointDurable = true
    checkpointClearPending = true
```

并且：

```ts
refresh()
```

会优先：

```ts
retryClearPending()
```

而不会重新执行整个任务。

同时你加了测试：

```text
clear 第一次失败
↓
checkpoint 仍存在
↓
storage 恢复
↓
refresh
↓
只重新 clear
↓
collect 仍然只执行一次
```

这点做得很好。

# 11. 现在还剩一个我认为值得修的恢复边界问题

这是这次修完后，我现在最想继续挑出来的 correctness 问题。

持久化 checkpoint phase 仍然只有：

```ts
type AutoRecordCheckpointPhase =
  | 'capturing-user'
  | 'awaiting-reply';
```

但是内存现在实际上已经存在第三种状态：

```text
history 已写成功
checkpoint 尚未 clear
```

也就是：

```ts
checkpointClearPending = true
```

问题是：

> `checkpointClearPending` 只存在内存。

假设：

```text
assistant 回复已捕获
↓
transcript 保存成功
↓
history 保存成功
↓
clear checkpoint 失败
↓
checkpointClearPending = true
↓
浏览器立刻刷新 / content script 被销毁
```

新的 JS context 重新读取 storage 时只看到：

```text
phase = awaiting-reply
```

它不知道：

```text
history 已经成功写过了
```

因此可能重新：

```text
collect reply
↓
persist transcript
↓
emit history
↓
clear
```

你现在大部分后续操作本身有幂等保护，所以**大概率不会产生严重重复数据**。

但从状态机设计上说，这仍然不够完整。

# 12. 我建议加真正的第三阶段

例如：

```ts
type AutoRecordCheckpointPhase =
  | 'capturing-user'
  | 'awaiting-reply'
  | 'completed-pending-clear';
```

流程：

```text
capturing-user
      ↓
awaiting-reply
      ↓
persist transcript/history
      ↓
completed-pending-clear
      ↓
clear checkpoint
```

那么刷新以后：

```text
completed-pending-clear
```

直接：

```text
retry clear
```

而不会重新 collect。

这是我现在认为**最值得补的一个小型正确性改进**。

# 13. Manual History 虽然并发问题修了，但存储扩展性问题还在

现在 `manual-history-grouping.ts` 仍然保存：

```ts
{
  tasks: {...},
  allocations: {...}
}
```

然后每条消息：

```text
storage.get(整个对象)
↓
cloneState(整个对象)
↓
修改一个节点
↓
storage.set(整个对象)
```

而 `allocations`：

```text
runId1
runId2
runId3
...
```

还没有 GC。

所以现在是：

> **并发 correctness 修好了，scalability 还没有解决。**

小规模完全没问题。

如果以后自动记录成千上万条：

```text
N = 100
没感觉

N = 5,000
开始明显

N = 50,000
就不应该再用一个巨大 JSON
```

IndexedDB

# 15. `readStoredState()` 还有一点防御性不足

现在：

```ts
if (
  !isRecord(candidate.tasks) ||
  !isRecord(candidate.allocations)
) {
  return empty
}

return cloneState(candidate as ManualHistoryGroupingState)
```

也就是说只检查了：

```text
tasks 是对象
allocations 是对象
```

内部：

```text
task.events
event.acts
grouping fields
```

并没有完整 schema 验证。

虽然 `cloneState()` 出错会被 catch，然后：

```text
return createManualHistoryGroupingState()
```

但这意味着：

> 一小块存储损坏可能让整个 grouping state 被当成空状态。

之后可能重新从：

```text
nodeIndex = 0
```

开始分配。

最好加：

```ts
manualHistoryGroupingStateSchema
```

完整校验 persisted state。

不要 silently：

```text
corrupt
→ empty
```

更合理是：

```text
corrupt
↓
quarantine / log
↓
repair or refuse allocation
```

这属于中优先级的数据完整性改进。

# 16. Runtime messaging 现在有一点“local/cloud 混在一起”

现在：

```ts
runtimeOperationSchema
```

里面同时有：

```text
AW_CLOUD_AUTH_STATUS
AW_CLOUD_AUTH_SIGN_IN
AW_CLOUD_AUTH_SIGN_OUT

AW_HISTORY_ENTRY_ENQUEUE

AW_MANUAL_HISTORY_GROUPING_ALLOCATE

AW_LOG_DELIVERY_STATUS
```

然后 service worker：

```text
如果 manual grouping
    → local handler

否则如果 runtime operation
    → cloud runtime
```

甚至 `cloud-runtime-handler` 为了 union exhaustive，还要知道：

```text
AW_MANUAL_HISTORY_GROUPING_ALLOCATE
```

并返回：

```text
OPERATION_UNAVAILABLE
Manual history grouping is handled by the local runtime.
```

这不算 bug。

但是架构语义上略别扭。

以后可以变成：

```text
BackgroundRuntimeRouter

├─ LocalRuntimeHandler
│    └ manual history grouping
│
└─ CloudRuntimeHandler
     ├ auth
     ├ logs
     └ delivery
```

这样：

```text
CloudRuntimeHandler
```

完全不需要知道：

```text
manual history grouping
```
