## 1. `completed-pending-clear` 已经真正补上了

这是刚才我最建议补的东西，现在已经实现了。

Checkpoint：

```ts
type AutoRecordCheckpointPhase =
  | 'capturing-user'
  | 'awaiting-reply'
  | 'completed-pending-clear';
```

现在完整状态机变成：

```text
捕获发送事件
     ↓
capturing-user
     ↓
捕获用户消息
     ↓
awaiting-reply
     ↓
收集 assistant reply
     ↓
保存 transcript / history
     ↓
completed-pending-clear
     ↓
clear checkpoint
```

比之前完整很多。

更重要的是恢复逻辑：

```ts
if (checkpoint.phase === 'completed-pending-clear') {
    clearCheckpoint(...)
    return;
}
```

也就是说刷新后：

```text
completed-pending-clear
        ↓
只清理
```

而不是：

```text
重新 capture
重新 collect
重新 emit history
```

这才是真正的 durable state machine。

## 3. Manual History 数据损坏处理也改对了

之前：

```text
stored state 有问题
↓
当成 empty state
```

这个很危险，因为可能重新：

```text
nodeIndex = 0
actIndex = 0
```

导致历史坐标冲突。

现在你给完整树建立了：

```ts
manualHistoryActStateSchema
manualHistoryEventStateSchema
manualHistoryTaskStateSchema
manualHistoryGroupingStateSchema
```

然后：

```ts
const parsed =
    manualHistoryGroupingStateSchema.safeParse(value);

if (!parsed.success)
    throw ...
```

现在变成：

```text
持久化数据损坏
      ↓
拒绝继续 allocation
```

也就是 **fail closed**。

这是正确的数据完整性策略。

## 4. Conversation URL grouping 也更稳定了

这个改动虽然看起来小，其实挺重要。

以前：

```text
https://chatgpt.com/c/abc?model=gpt-5

https://chatgpt.com/c/abc?temporary-chat=false#latest
```

有可能因为 URL 不一样被当成不同 Act。

现在提取：

```text
/c/<conversationId>
```

最终统一成：

```text
https://chatgpt.com/c/abc
```

因此：

```text
同一个 ChatGPT conversation
           ↓
同一个 Act
           ↓
nodeIndex 0
nodeIndex 1
nodeIndex 2
...
```

这个语义比直接拿 `location.href` 当 identity 正确得多。

# 6. 现在还剩一个很小但值得知道的 crash window

目前顺序是：

```ts
await persistReplyAndHistory(...);

await persistCheckpoint({
  phase: 'completed-pending-clear'
});
```

也就是说理论上仍存在极小窗口：

```text
history 已经写成功
        ↓
【浏览器/页面在这里突然崩掉】
        ↓
completed-pending-clear 尚未落盘
```

重启以后存储里还是：

```text
awaiting-reply
```

可能重新进入 reply collection。

这不属于我现在认为需要阻止合并的问题。

因为要完全消灭这种窗口，就开始涉及类似：

```text
两阶段提交
transactional outbox
reply-captured phase
```

这种更复杂的协议。

如果以后特别追求极端情况下的 exactly-once，可以再变成：

```text
capturing-user
      ↓
awaiting-reply
      ↓
reply-captured
      ↓
history-written
      ↓
completed-pending-clear
```

但**我不建议现在为了这个继续扩张状态机**。

当前程度已经足够工程化。

# 7. 现在真正值得注意的是“腐坏数据如何恢复”

现在 fail closed 是正确的。

但用户一旦真的遇到：

```text
manualHistoryGrouping state corrupted
```

会：

```text
拒绝继续 allocation
```

安全是安全了，但是目前缺少：

```text
Repair / Reset
```

路径。

以后最好做：

```text
检测 corruption
      ↓
复制到 quarantine key
      ↓
记录错误
      ↓
让用户选择 Reset local grouping state
```

例如：

```text
anyworkflow.manualHistoryGrouping.v1.corrupt.<timestamp>
```

保留坏数据后再重建。

这个属于 **P2 运维体验**，不是 correctness blocker。
