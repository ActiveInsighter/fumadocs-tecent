# 一、现在的整体架构其实已经挺像一个“小型工作流虚拟机”了

你现在的核心链路是：

```text
Queue DSL
    ↓
WorkflowQueueDocument
    ↓
QueueProgram
    ↓
Actions
    ↓
InstructionProgram
    ↓
WorkflowRuntime
    ↓
InstructionInterpreter
    ↓
PrimitiveInstructionExecutor
    ↓
Drivers
    ↓
Chrome / ChatGPT DOM
```

而且这不是我自己概括的，你现在的架构文档就是这么定义的。`workflow` 保留业务语义，`actions` 只负责编译，`runtime` 管 PC、寄存器、等待、失败和 instruction dispatch，`drivers` 才真正碰 DOM 和浏览器环境。

这个设计和你之前想要的：

> 上层像高级语言，底层像汇编，消息队列最终编译成具体操作

已经基本吻合了。

尤其现在：

```text
send message
capture user message
collect reply
navigate
reload
```

不再都是 `engine.ts` 里面随手调用 DOM，而是逐渐走成：

```text
业务动作
↓
Action Compiler
↓
Primitive Instruction
↓
Runtime
↓
Port / Driver
```

这是这次重构里最有价值的部分。

光 import 就已经能看出它仍然承担了大量跨层职责。

所以你现在的架构其实处于：

```text
        新架构
Actions / Runtime / Drivers
          ↑
          │
    ┌─────┴─────┐
    │ engine.ts │
    └───────────┘
       旧编排核心
```

而不是最终理想的：

```text

       ↓

       ↓

       ↓
```

**不要重写 `engine.ts`。**

```text

├─ ReplyCollectionFlow
├─ RecoveryCoordinator
├─ DeferredReplyCoordinator
├─ NavigationCoordinator
├─ TerminalHistoryCoordinator
└─ RunLifecycleCoordinator
```

最后 `QueueRunner` 应该接近：

```ts
class QueueRunner {
  async run() {

      const node = ...
      await this.executor.execute(node)
```

而不应该自己知道：

> reload 怎么恢复、reply timeout 怎么恢复、历史怎么拼 Task/Event/Act、DOM 怎么绑定消息……

# 五、这次新代码里我认为最值得马上修的，是一个真正的并发问题

这个比 80KB 文件还更应该优先。

现在：

```ts
let storageQueue: Promise<void> = Promise.resolve();
```

用这个序列化：

```ts
chrome.storage.local
```

里的 `manualHistoryGrouping` 分配。

单标签页内确实安全：

```text
allocate A
    ↓
allocate B
    ↓
allocate C
```

但是 Chrome 扩展的不同 content script 是不同 JS execution context。

假设：

```text
ChatGPT Tab A
ChatGPT Tab B
```

它们各自都有自己的：

```ts
storageQueue
```

于是可能出现：

```text
Tab A                    Tab B

storage.get()
  ↓
state = S

                         storage.get()
                           ↓
                         state = S

allocate A               allocate B

S → S+A                  S → S+B

storage.set(S+A)
                         storage.set(S+B)
```

最后：

```text
A 的更新丢了
```

这就是典型：

```text
read
modify
write
```

竞争。

而你的注释写的是：

> Persistent allocation store shared by all content-script instances.

这个“共享存储”是真的，但 **锁并没有跨 content-script 共享**。

### 我建议改成

```text
Content Script A ─┐
                  │
Content Script B ─┼→ Service Worker
                  │       ↓
Content Script C ─┘  HistoryGroupingService
                          ↓
                  chrome.storage.local
```

让 background/service worker 成为：

> **manual history grouping 的唯一写入者**

这样自然就实现单写者模型。

这是我给的 **P0/P1 级优化**。

# 六、第二个很重要的问题：Checkpoint 的错误处理破坏了“durable”的承诺

这个地方我比较不赞成。

当前：

```ts
private async persistCheckpoint(...) {
  this.pendingCheckpoint = checkpoint;

  try {
    await this.checkpointStore.save(checkpoint);
  } catch (error) {
    await this.logFailure(...)
  }
}
```

也就是说：

```text
保存 checkpoint 失败
        ↓
打印日志
        ↓
继续执行
```

而 `handleManualSend()` 是：

```text
persist checkpoint
        ↓
executeOwnedCheckpoint()
```

因此可能：

```text
准备自动记录
↓
Chrome storage 写入失败
↓
只 warn
↓
继续 capture user
↓
继续等待 assistant
```

这和“durable checkpoint”设计目标是冲突的。

更危险的是 `clearCheckpoint()`：

```ts
try {
  await checkpointStore.clear()
} catch {
  log...
}
```

失败也吞掉。

然后调用方继续：

```ts
this.pendingCheckpoint = null;
```

所以可能：

```text
assistant 已记录
↓
clear storage 失败
↓
内存认为没有 checkpoint
↓
刷新页面
↓
旧 checkpoint 又回来了
↓
重新 replay
```

Transcript 本身做了 `upsert`，按 `runId + messageIndex` 有一定幂等保护，这是好的。

但你不能依赖后面所有副作用永远帮你去重。

### 建议

把 checkpoint 操作区分：

```text
Best-effort persistence
Critical persistence
```

比如：

```ts
await checkpointStore.save(checkpoint);
```

对于：

```text
before external side effect
```

失败就应该：

```text
STOP
```

而不是：

```text
WARN + CONTINUE
```

这其实和你之前对 `CLICK_SEND` 的设计思想完全一致：

```text
CHECKPOINT
↓
CLICK_SEND
```

既然 Runtime 的发送 side effect 已经认真解决这个问题，AutoRecord 也应该遵循同一原则。架构文档本身也强调了 side effect 前 durable prepare boundary。

# 八、Runtime 现在最大的问题不是设计差，而是“类型安全只做到一半”

例如：

```ts
MachineState {
  registers: Record<string, unknown>
}
```

然后业务层不得不：

```ts
asCapturedUserMessage(...)
asReplyCollectionResult(...)
asReplySnapshot(...)
```

自己运行时判断。

`engine.ts` 有一套：

```ts
asReplySnapshot
asReplyCollectionResult
```

`AutoRecordController` 又有：

```ts
asCapturedUserMessage
asReplyCollectionResult
```

这说明：

> Instruction 已经 typed，但 Register 还是 untyped VM memory。

短期没问题。

长期我建议做：

```ts
Program<I, O>
```

或者至少：

```ts
interface ProgramResultMap {
  'send-message': ReplySnapshot;
  'collect-reply': ReplyCollectionResult;
  'capture-user-message': CapturedUserMessage;
}
```

让调用端接近：

```ts
const result = await runtime.executeProgram(
  compileCaptureUserMessageProgram(...)
);

// result 已经是 CapturedUserMessage
```

而不是：

```ts
state.registers["user-message.capture"]
```

然后再手动解码。

### 不建议

把 Runtime 做成大量泛型黑魔法。

你这个项目不需要追求类型体操。

简单做到：

```text
Instruction 内部 registers = unknown

Action API 外部 = typed
```

就够了。

# 九、`ManualSendObserver` 的 Enter 判断还有一个边缘风险

现在监听：

```ts
keydown
```

并且：

```ts
Enter
!shift
!ctrl
!alt
!meta
!isComposing
```

就提前接受这个发送意图。

问题是你监听在 capture phase：

```ts
document.addEventListener('keydown', handler, true)
```

意味着：

```text
你的 handler
↓
ChatGPT 自己的 handler
```

所以你看到：

```text
Enter
```

并不能百分百证明：

```text
ChatGPT 最终真的发送了
```

ChatGPT 以后如果加入：

```text
候选菜单
命令菜单
mention
特殊输入模式
```

某些 Enter 可能会被官方逻辑拦截。

而且你用了：

```ts
750ms
```

时间窗口去重：

```text
keydown
↓
750 ms 内 submit
↓
submit 被去重
```

如果第一个 keydown 是误判，就会把后面的真实事件一起吞掉。

### 更稳的模型

不是：

```text
keydown == send
```

而是：

```text
keydown == send intent candidate
```

然后真正确认：

```text
DOM 中出现新的 user turn
```

你后面的 `CAPTURE_USER_MESSAGE` 其实已经具备这种确认能力。

所以整体不算 bug，但建议把 observer 语义明确成：

```text
ManualSendCandidateObserver
```

并让 dedupe key 从单纯：

```text
timestamp
```

升级到类似：

```text
conversation
+ normalizedDraft
+ baseline user count
```

时间只作为辅助。

# 十、Manual History Grouping 还有一个长期存储增长问题

现在整个状态大概是：

```text
tasks
 ├ month
 │  └ events
 │      └ acts
 │
allocations
 ├ runId1
 ├ runId2
 ├ runId3
 ├ ...
```

而每次 `allocate()`：

1. 读取整个对象
2. clone 整个对象
3. 修改
4. 整个重新 `storage.set()`

并且：

```ts
allocations
```

看起来没有 GC。

刚开始：

```text
100 条消息
```

没感觉。

以后：

```text
10,000
50,000
100,000
```

会变成：

```text
每次 O(N) clone
+
每次 O(N) serialize
+
storage quota
```

### 建议不要一个巨型 JSON

改成：

```text
manual-history/task/2026-08

manual-history/event/2026-08-27

manual-history/act/<conversationId>

manual-history/allocation/<runId>
```

或者更彻底：

```text
IndexedDB
```

我更倾向：

> **运行/恢复状态：chrome.storage.local**

> **大量不断增长的历史索引：IndexedDB / 后端**

# 十一、Conversation Gate 本身写得挺干净

现在这个：

```ts
ConversationExecutionGate
```

只维护：

```text
owner = queue | manual | null
```

并且明确拒绝同 owner 的重入 acquire。

这个比直接拿 Zustand：

```ts
state.running
```

当互斥锁强很多。

这是一个好设计。

不过 AutoRecord 又同时检查：

```ts
!queueActive()
&& gate.owner === null
```

实际上现在存在两套“谁有执行权”的判断：

```text
Zustand running
ConversationExecutionGate
```

这里建议长期逐渐收敛：

```text
执行互斥真相
       ↓
ConversationExecutionGate
```

而：

```text
state.running
```

只负责：

```text
UI 展示 / lifecycle status
```

不要让两个状态长期都承担 correctness。

否则未来很容易：

```text
state.running = false
gate.owner = queue
```

或者反过来。

你现在其实**已经有大约 70%～80% 是这个样子了**。

所以我不建议再来一次“大重构”。

现在最合适的是：

> **保持现有 Runtime / Actions / Drivers 基本不动，修两个 correctness 问题，然后持续把 `engine.ts` 的 orchestration 一块一块搬出去。**

这会比再设计一套新架构健康得多。

最后给这个分支一句评价就是：

**已经从“功能很多的 Chrome 自动化脚本”跨进了“有 VM、Action lowering、Driver boundary、durable recovery 的工作流执行系统”，底层设计已经不错；现在最大的瓶颈已经从底层抽象不足，转移成上层编排过重、持久化原子性和跨标签页并发安全。** 这三个问题解决之后，整体架构就会相当扎实。
